> **Consolidation sub-stage 3 (final step).** The minimal fixed scaffold for program pages: the order-bearing skeleton the kit's blocks compose onto. Sibling to the Component Register — the Register is the _kit_ (what blocks exist), this is the _skeleton_ (what's anchored where). Together they are the two-part Stage-2 input.

Scope: **order-bearing** — anchored regions / sequence, not just a presence checklist. Fixed-position may still be optional-presence. Decided last, per the Stage 1.5 method. Input: the locked 18/18-Confirmed kit + the cross-program matrix.

## The test (applied to every candidate)

A block earns a **fixed position** only if it passes BOTH:

- **(a) Fits every program** — genuinely present, or honestly synthesizable, on all four (PA · WJ · SFA · AB). Universality by fact, not intent.
- **(b) Position is load-bearing** — _where_ it sits materially helps the user's scan. A block that could sit anywhere without hurting the scan fails (b) even if it passes (a).

Bias, per method: **resist promotion.** Every fixed element re-imposes a constraint on pages proven structurally different. Default = "not fixed — composed freely." Fixed-position can still be **optional-presence** (an anchored slot a program may leave empty without the skeleton looking broken).

Not a template — a thin skeleton of anchored _regions_; everything between anchors is free kit composition. Not a claim that anchored blocks are the _only_ content in a region — just that _if present_, they sit there.

## The scaffold — three tiers

A program page is: **[TOP region] → free composition from the kit → [TAIL region].**

**Why the middle tier exists.** Some blocks aren't on every program — so they can't be _mandatory_ — but _when a program uses them_, where they sit is load-bearing. Forcing them fails (a); leaving position to free composition wastes a scan cue. "Anchored-when-present" = **optional presence, fixed position when present.**

### Tier 1 — Hard anchors (mandatory + positioned)

**Overview → page top (first block).** Mandatory: every program needs an opening orientation; "no intro" only ever reads as broken. Load-bearing: it's the first thing scanned — being first _is_ the function. A page that opens on a stat strip or accordion disorients.

**Apply CTA → top region (may repeat).** In the top region (above the fold in scan terms), and may repeat adjacent to the apply-steps block. Mandatory: all four route to an apply action — portal (PA/WJ/AB) or encrypted JotForm (SFA); the route is a value on the block, not a reason to exclude. Load-bearing: primary conversion; fixes PA's scattered-CTA problem.

**Contact → page tail.** Last / closing region of the body. Mandatory: all four carry a program contact email. Load-bearing: contact is universally scanned-for at the end; a fixed tail slot means users never hunt for it.

### Tier 2 — Anchored-when-present (optional presence, fixed position when composed)

**Hero / header-summary → very top.** Position when present: the very top, above (or fused with) the Overview. Optional: composed by WJ + AB today; available to any program to synthesize from its own fields (3b: available/synthesizable, never forced); SFA declines on confidentiality-tone grounds. Why positioned: a scannable page-top summary only works at the top — if it exists its slot is fixed; if not, no gap shows.

**Stat / figure strip → top region, by the Overview.** Position when present: the opening region, adjacent to the Overview, so impact reads at the top of the scan. Optional: present on PA/WJ/AB; **SFA declines** — a risk/emergency program has no scale figures to tout, and its confidentiality-first tone argues against a "how many we've helped" strip (absence by design, not a content gap). Why positioned: impact figures are a top-of-scan communication; burying them mid-page wastes them.

### Tier 3 — Soft tail

**FAQ → recommended near Contact.** Passes (a) — real block on all four (EN emptiness is a content/QA gap, not structural absence). Fails (b) at the anchor bar: exact position among tail blocks isn't load-bearing — near-the-end is conventional, but nothing breaks if a caveat or directory sits between it and Contact. Recorded as recommended ordering, not a fixed slot.

## Deliberately NOT in the scaffold

- **Apply steps** — fits every program but has no single fixed position (WJ nests it in variant-paths). Region-associated, not slot-fixed.
- **Key-value strip** — absent on SFA; and where present, position isn't load-bearing (flat facts sit with their section).
- **Selection / Contractual text** — fail (a) in shape: SFA has no jury (committee) and near-empty contract. The contractual block's defining property is that it _degrades to near-empty_ — the opposite of a load-bearing fixed slot.
- **Everything program-specific** (timeline, directory, variant-paths, when-to-apply, callout, download-list, card grid) — one-to-three programs each; optional kit blocks by definition.

## Resulting skeleton (one line)

> **[Hero — if composed] → Overview (mandatory, first) + Apply CTA (mandatory, top region) + [Stat strip — if composed, by the overview] → … free composition from the 18-block kit (apply steps, support, eligibility, selection, timeline, directory, etc., in whatever order each program warrants; CTA may repeat by the steps) … → [FAQ — recommended] → Contact (mandatory, tail).**

Three hard anchors, two anchored-when-present, one soft tail. Nothing else fixed; nothing new made mandatory. Everything between the top region and the tail is free kit composition — the point being that the programs are structurally different and the scaffold stays deliberately thin.
