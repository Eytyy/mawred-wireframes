> **Living doc.** The kit of feature-defined blocks the client composes each program page from. Built incrementally via the page-by-page component breakdown (Stage 1.5). Each program's breakdown reads from and writes to this register: reuse a block if it fits, define a new one if it doesn't.

## How to read this

- **Blocks are defined by feature/treatment, not intent.** "Headline + text," "timeline," "accordion" — never "eligibility" or "grant amount." The same block hosts different meaning on different pages.
- **Used by** tracks which programs currently compose with the block — this is what tells us later whether something is near-universal (kit staple) or a one-off.
- **Recurrence state** _(separate axis from Status)_ — is this pattern spreading? `PA-only so far` · `Predicted to recur` (audit/matrix says other programs have it in some shape → later breakdowns look for it first) · `Confirmed recurring` (a second program actually reused it — only reachable from Wijhat onward).
- **Latent / graduated-from** — the highlight column for these text-heavy pages. For a composite block still holding fused content, the sub-blocks that _could_ graduate out. For a graduated block, what it came out of. This is where "this wall of text can be pulled apart" is recorded.
- **Editor-facing name (intent label)** — the label a WordPress content editor would recognize. The register stays _treatment-defined_ analytically (keeps the kit small + honest about what recurs); this column carries _intent_ so the dev handoff gives both. One treatment-defined block under the hood (one ACF flexible-content layout / Gutenberg block the dev builds + maintains once), surfaced to editors via intent-named presets/patterns + help text. Single-use blocks are fine — avoid _unlabelled_ blocks, not single-use ones. _(Spec-level note, not in the register: the "block kit composed per program, no unified template" approach maps directly onto ACF Flexible Content or Gutenberg block patterns — the grain of WordPress, both able to carry an intent label over a treatment-defined implementation.)_
- **Status:** _Proposed_ (surfaced, not yet confirmed) · _Confirmed_ (settled block in the kit) · _Under review_.
